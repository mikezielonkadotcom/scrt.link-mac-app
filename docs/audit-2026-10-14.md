# Scrt.link Mac App: performance and security audit

Date: 2026-10-14
Scope: `main` at `9f21160` (v1.6.1), every file under `Sources/`, `Resources/`, `tests/`, `scripts/`, the three shell scripts, and the signed-release workflow.
Method: full source read, baseline run of the five headless suites (all passing), an optimized comparison build, and a review of the trust boundaries between Swift, the hidden harness, scrt.link, GitHub Releases, and the local disk.

This report lists findings only. Nothing below has been changed in the code except the two small testability seams described at the end, which keep behavior identical.

## Summary

The app's core security design is sound and better than most small menu-bar utilities: the token lives in Keychain with a careful legacy migration, secret plaintext never touches disk, the updater pins the download host and path, verifies bundle ID, version, Apple team, signature and Gatekeeper before installing, and the release pipeline is gated, pinned to commit SHAs, and keeps secrets out of argv and logs.

The findings that matter most:

| ID | Severity | Area | One line |
|---|---|---|---|
| P1 | High | Performance | Release binaries are built without optimization (`-Onone`) |
| S1 | Medium | Security | Embedded web view trusts any host that merely contains `scrt.link` |
| S2 | Medium | Security | Links from web content are opened with any URL scheme |
| S3 | Medium | Security | The hidden crypto harness is Web Inspector attachable in release builds |
| S4 | Medium | Privacy | Bearer links are copied to the clipboard without the concealed marker |
| P2 | Medium | Performance | Updater runs `ditto`, `codesign`, `spctl` and a bundle copy on the main thread |
| P3 | Medium | Performance | A WebKit content process is spawned at launch even in native mode |

Everything else is low or informational.

## Security findings

### S1. Medium: embedded web view trusts any host containing "scrt.link"

`Sources/WebViewController.swift:237` decides what stays inside the app's web view with `host.contains("scrt.link")`. That is a substring match, so `scrt.link.example.com`, `notscrt.link`, or `scrt.linkattacker.com` all count as scrt.link. Any page that scrt.link links to on such a domain would render inside the app's own window, which users treat as the trusted scrt.link surface. Phishing inside a trusted frame is the risk.

Fix: compare exactly. Accept `host == "scrt.link"` or `host.hasSuffix(".scrt.link")`, and consider also honoring the configured custom host.

### S2. Medium: web content can launch arbitrary URL schemes

`Sources/WebViewController.swift:239`, `:245` and `:256` hand `NSWorkspace.shared.open(url)` whatever URL the page produced. `NSWorkspace.open` dispatches by scheme, so a crafted link or `window.open` from embedded content could trigger `tel:`, `file:`, `x-apple.systempreferences:`, or any third-party custom scheme registered on the Mac. This is a well known WebKit-wrapper footgun.

Fix: allow only `http` and `https` before opening externally, and cancel everything else.

### S3. Medium: the harness web view is inspectable in release builds

`Sources/ScrtLinkAPI.swift:75-77` turns on `setInspectable:` unconditionally. The hidden harness holds the bearer token and the plaintext secret in JavaScript scope during a create. Attaching requires the same user and Safari's Develop menu, so this is not remote, but a release build should not expose that surface, and it also widens what a malicious local process can reach through Safari's remote inspection protocol.

Fix: gate it behind `#if DEBUG`, or a hidden `defaults write` flag that is off by default.

### S4. Medium: bearer links land in the clipboard without the concealed marker

The link's `#` fragment is the decryption key, so every copy is a credential copy. `Sources/NativeSecretFormView.swift:238-242` (auto-copy on success), `Sources/HistorySidebarView.swift:493-497`, and `Sources/SecretLogWindow.swift:340-346` write to `NSPasteboard.general` with only the `.string` type. Clipboard managers (Paste, Maccy, Alfred, Raycast) will record and persist every link, including into their own synced histories.

Fix: also declare the `org.nspasteboard.ConcealedType` type (the de facto standard that password managers use) so compliant clipboard managers skip the entry. Optionally offer a preference to clear the clipboard after a timeout.

### S5. Low to medium: history stores bearer links in a plaintext preferences file

`Sources/SecretHistoryStore.swift` keeps up to 500 links in `~/Library/Preferences/com.mikezielonka.scrt-link.plist`. The README discloses this honestly, and Preferences are user-only on disk, but the file is included in Time Machine and iCloud Desktop/Documents-style backups of `~/Library`, is trivially readable by any process running as the user, and survives app removal.

Options, in order of effort: (1) store the history file under `~/Library/Application Support/<bundle id>/` with `0600` permissions and a `com.apple.metadata:com_apple_backup_excludeItem` attribute so it stays out of backups; (2) encrypt the array with a random key held in the Keychain item next to the token; (3) make retention user-configurable (the sidebar's 24 hour window suggests most links are only useful briefly).

### S6. Low: custom host is not validated as a hostname

`Sources/PreferencesWindow.swift:293-301` strips `https://` and slashes, then `Sources/ScrtLinkAPI.swift:193-194` passes the value to scrt.link's client module as `opts.host`, which then POSTs the bearer token to `https://<host>/api/v1/secrets`. The value is the user's own setting, so this is not an injection, but a paste like `secrets.example.com:8443/foo` or `user@host` goes through unchecked and sends the token somewhere unexpected.

Fix: parse with `URLComponents(string: "https://" + value)` and accept only when scheme is https, path is empty, and there is no port, user, query or fragment.

### S7. Low: the harness has no Content Security Policy

`Resources/harness.html` imports scrt.link's client module and trusts it fully; that is the documented design. A CSP would still bound the blast radius if that module were ever compromised or served a redirect: `script-src 'self' https://scrt.link 'unsafe-inline'; connect-src https://scrt.link <custom host>; default-src 'none'`. The custom host makes a static CSP awkward, so inject the meta tag from Swift when the harness loads.

### S8. Low: the harness shares the persistent website data store with the embedded web UI

`Sources/ScrtLinkAPI.swift:65-68` builds `WKWebViewConfiguration()` with the default data store, so the harness's same-origin fetches to scrt.link carry whatever cookies the embedded web UI set. A `WKWebsiteDataStore.nonPersistent()` store keeps the API path cookie-free and stateless, and is what you want for a crypto sandbox.

### S9. Low: updater verifies the extracted bundle, then copies it, then installs the copy

`Sources/UpdateManager.swift:161-171` runs `verifyUpdate` on `newApp` inside a temp directory and then `copyItem` to a staged path beside the installed app. Verification should run on the exact bytes that will be moved into place. The temp directory is per user, so the practical exposure is small, but moving the `verifyUpdate` call after the copy (on `stagedURL`) closes the window for free.

### S10. Low: update check ignores the HTTP status

`Sources/UpdateManager.swift:48-63` parses the body without looking at `response`. A `403` rate limit body has no `tag_name`, so it degrades to "Could not parse release information" in interactive mode. Checking the status would let the message say "GitHub rate limited the check, try again later".

### S11. Informational: non-link navigations stay inside the app

`Sources/WebViewController.swift:244-248` only pushes `.linkActivated` navigations to the browser. Redirects, form posts and JavaScript `location` changes to third-party hosts load inside the app window. Combined with S1 this is the second half of the trusted-frame concern.

### S12. Informational: hotkey prefills the secret field with the clipboard

`Sources/main.swift:152-154` reads `NSPasteboard.general` on the global hotkey and drops it into the secret text area. This is the intended workflow and nothing is sent until the user clicks Create, but a user who hits ⇧⌘S while a password is on the clipboard will see it selected in a window. Worth a sentence in the README's hotkey description.

### S13. Informational: `build.sh` uses `set -e` only

`release.sh` and the tests use `set -euo pipefail`; `build.sh` does not. An unset variable or a failing `cp | ...` pipeline would not stop the build.

### What is already strong

- Keychain storage with `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, no silent fallback on Keychain errors, and the legacy token moved only after a successful write (`Sources/KeychainStore.swift`).
- No plaintext secret or token in the diagnostic report (covered by `tests/ScrtLinkAPITests`).
- JS interpolation goes through JSON encoding, so secret text cannot break out of the generated call (`Sources/ScrtLinkAPI.swift:297-311`).
- Request IDs stop stale timeouts and late results from crossing requests.
- Download URL pinned to `https://github.com/<owner>/<repo>/releases/download/v<version>/<name>`; bundle ID, version, team ID, `codesign --strict --deep -R`, and `spctl` all checked before install; backup kept after a successful relaunch.
- Release workflow: `contents: read` by default, `persist-credentials: false`, every action pinned to a SHA, secrets loaded only after tests on a separate runner, disposable Keychain, SHA256 verified before publish and the tag and asset digest verified afterwards, `main` only.
- `ci-signing.py` keeps both passwords out of argv, logs and artifacts, and validates the app-specific password format.

## Performance findings

### P1. High: release builds are unoptimized

`build.sh` passes no optimization flag to `swiftc`, so every build, including the one `release.sh` signs and notarizes, is `-Onone`. Swift at `-Onone` keeps every retain/release, generic specialization is off, and arrays, `Codable` and string handling run several times slower. The shipped binary is also carrying the debug-shaped code.

Measured on this machine (Swift 6.4):

| Build | Binary size |
|---|---|
| Current `build.sh` (no flag) | 976,768 bytes |
| Same sources with `-O -wmo` | 531,288 bytes |

Fix: add `-O -wmo` to `build.sh`. Both existing test scripts that compile sources directly can stay at `-Onone` for faster iteration.

### P2. Medium: the updater blocks the main thread during install

`Sources/UpdateManager.swift:118-135` closes the "Updating..." progress window as soon as the download finishes, then `installUpdate` runs entirely on the main actor: `copyItem` of the ZIP, `ditto -x -k`, `codesign --verify --deep`, `spctl --assess` (which can contact Apple and take several seconds), and a `copyItem` of the whole `.app`. Each `run()` call does `waitUntilExit()` synchronously. The user sees a beachball with no window explaining why.

Fix: keep the progress window up and move the extraction and verification to a detached `Task`, hopping back to the main actor only for the final move and the alert.

### P3. Medium: a WebKit process is spawned at launch in native mode

`Sources/WebViewController.swift:17-32` creates the embedded web UI `WKWebView` in `init`, before the mode is known. In the default native mode that view is never shown, but WebKit still starts a WebContent process and a networking process for it, costing tens of megabytes and launch time for a menu-bar app that users keep running all day.

Fix: create the web view lazily in `applyMode()` the first time `.web` is selected, and tear it down when the user switches back.

### P4. Low: first Create pays the harness cold start

`ScrtLinkAPI.shared` is first touched from `createTapped`, so the first secret waits for WebKit startup plus the network fetch of scrt.link's client module. That is a deliberate privacy trade-off (no network until the user acts). A middle ground is to warm the harness when the main window is shown and a token is present.

### P5. Low: every history read decodes the full array

`SecretHistoryStore.load()` decodes up to 500 entries from JSON on each call; `add` decodes and re-encodes; the sidebar and the log window each decode again on every `.secretHistoryChanged` notification. At 500 entries this is low milliseconds, so it is not user visible, but an in-memory cache invalidated on write would make the change notifications free.

### P6. Low: toolbar rebuilt on every window show

`Sources/WebViewController.swift:131-141` removes and re-inserts every toolbar item each time `applyMode()` runs, which `showWindow()` calls on every menu bar click. Rebuild only when the mode actually changed.

### P7. Low: Keychain read on every `hasToken`

`KeychainStore.apiToken` performs `SecItemCopyMatching` and a `UserDefaults` legacy check each time, and the sidebar calls it on each token-change notification. Cheap, but a memoized value invalidated by `setApiToken` would avoid repeated Keychain round trips.

### P8. Informational: test hygiene

The offline harness test uses the default `WKWebsiteDataStore`, so it leaves `~/Library/WebKit/scrtlink-api-tests` behind on the developer's machine. Using a non-persistent store in tests (and in the harness, see S8) avoids that.

### What is already efficient

- Sidebar and log refresh timers run only while their windows are visible and reuse cards when the entry set is unchanged.
- Formatters are cached as statics.
- The update check is deferred three seconds after launch and never blocks the UI.

## Test coverage gaps found during the audit

- No test exercised the real form end to end: typing a secret, clicking Create, the result card, the clipboard, the history store, the sidebar card and the Secret Log row. The UI layout test seeds the store directly.
- Nothing tested the updater's security gates offline. `test-autoupdate.sh` needs network and Accessibility permission and only asserts that an alert appeared.
- The hotkey/Services prefill path and the forced switch back to native mode had no coverage.
- The error paths users actually hit (empty secret, missing token, API failure) were untested at the UI level.

The two new suites added alongside this report (`tests/test-e2e-native-flow.sh` and `tests/test-update-verification.sh`) close these gaps. They required two small seams: `ScrtLinkAPI.shared` became replaceable so a test can install an offline instance, and the updater's version compare, asset URL pinning and bundle verification moved into static functions that take their inputs explicitly. One deliberate tightening rode along: the asset URL check now also rejects a URL with userinfo or an explicit port, which GitHub never serves.

## Suggested remediation order

1. P1: add `-O -wmo` to `build.sh`. One line, measurable, zero risk.
2. S1 and S2 together in `WebViewController`: exact host match, scheme allowlist.
3. S3: gate `setInspectable:` behind `#if DEBUG`.
4. S4: add the concealed pasteboard type in one shared helper used by all three copy sites.
5. P2 and S9 together: move install work off the main actor and verify the staged copy.
6. P3: lazy web view.
7. S8, S6, S7, P6, then S5 as a product decision.
